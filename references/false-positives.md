# 常见假阳性场景

白盒漏洞校验中，某些场景容易被误判为漏洞（假阳性）。本文件列出这些场景、默认判断、判断理由、以及需要什么证据才能推翻默认。

遇到这些场景时，先按默认判断走，再主动找反例证据——找不到反例就维持默认。

---

## 场景 1：环境变量表示文件或目录路径

**默认判断**：攻击者不可控，不计为 Source

**理由**：
环境变量通常由部署配置（K8s ConfigMap、Docker ENV、systemd EnvironmentFile、.env 文件）或运维脚本在进程启动前设置，应用进程只读取。攻击者要修改环境变量，需要先获得主机层或容器编排层的权限——此时威胁模型已超出应用层漏洞范畴，不应计为应用层 Source。

**反例条件**（找到以下证据之一才能推翻默认，计为可控）：
- 程序内部显式 `setenv()` / `putenv()` 且值来自用户输入（如 HTTP 请求参数写入环境变量后再传给子进程）
- 部署文档或运行时配置明确允许用户传入该环境变量（如某些 Serverless 平台支持请求级环境变量覆盖）
- 通过 CGI 或特殊网关模式，HTTP 头部被映射为环境变量（如传统 CGI 把 `HTTP_*` 头部映射为环境变量）

**常见误判**：
看到 `getenv()` → `open()` / `File.read()` 就判定路径穿越或任意文件读取，未检查环境变量的实际设置来源。正确做法是先确定该环境变量由谁设置——若由部署/运维设置则默认不可控，举证到此为止；只有发现上述反例证据时才继续作为 Source 分析。
