# 敏感信息泄露

**适用**：被校验的主张是敏感信息落入日志、文件、控制台、HTTP 响应等持久化/输出渠道而泄露。

## 敏感信息定义

以下信息才被视为敏感信息。**凡是不属于本定义范围的字段，无论落入日志、文件、控制台、HTTP 响应还是其他输出渠道，都不认定为敏感信息泄露问题。**

仅明文或加密的认证凭据类信息（密码、Token、密钥、证书私钥、Cookie 等）、电话号码、邮箱地址视为敏感信息；用户名、昵称、ID、地址、非私钥的证书字段等不认定。**但当数据内容无法确定时（请求 body 结构未定义、data/msg 等通用容器内容不可追溯），按敏感信息处理**。

## 判断规则

- **必须有明确的落盘/输出操作**：敏感信息泄露问题必须存在明确的文件写入、日志记录、控制台输出、HTTP 响应返回等实际操作；若敏感信息仅停留在内存变量、方法参数、中间对象流转，未观察到任何实际写入持久化或输出渠道的行为，不认定为问题，禁止推测。
- 若只是记录异常信息（如 `log.error("...", e)`、`e.getMessage()`、`e.toString()`），没有证据证明异常信息中包含上述敏感字段，默认认定为无敏感信息。
- HTTP 错误响应中返回的异常信息，在没有证据证明包含上述敏感字段的情况下，默认认定为无敏感信息。
- 敏感信息仅被写入普通 JSON 对象（如构造 `JSONObject`、`Map`、DTO 等中间结构），未落入日志、文件、控制台、HTTP 响应等持久化/输出渠道的，不认定为敏感信息泄露问题。
- 记录对象时（如 `log.info(obj)`、`logger.debug(obj)`），应检查该对象的 `toString()` 是否做了特殊处理：若通过重写 `toString()`、`@ToString.Exclude`、脱敏注解或自定义实现排除了敏感字段，不认定为敏感信息泄露。
- 管道通过 `echo $password | mycmd` 传递密码：`echo` 是 shell 内建命令，不会把密码作为独立进程参数暴露，`ps` 等工具看不到密码，因此不视为命令行参数泄露密码的问题。
